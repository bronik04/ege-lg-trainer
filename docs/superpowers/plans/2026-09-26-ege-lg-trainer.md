# Тренажёр лексики и грамматики ЕГЭ — план реализации

> План для реализации по этапам. Отметки `- [ ]` показывают проверяемые результаты; написание продукта начнётся после просмотра и уточнения плана владельцем.

**Цель:** опубликовать на GitHub Pages статический тренажёр заданий 15–27 ЕГЭ по китайскому языку с теорией, проверкой правил, практикой и полным вариантом.

**Архитектура:** статические HTML, CSS, JavaScript и подготовленный при сборке банк JSON. Импорт и валидация источников выполняются локально перед публикацией; интерфейс только читает готовые данные. Объяснения хранятся вместе с заданиями, поэтому разбор работает без сервера.

**Стек:** браузерный JavaScript, CSS, Python для импорта и проверок данных, GitHub Actions и GitHub Pages. Без серверной базы, API и обязательного фреймворка.

**Замысел:** [проектный замысел](../specs/2026-09-26-ege-lg-trainer-design.md).

## Ключевые решения

- Целевой каталог — `ege-lg-trainer`, сейчас пустой. `lingvostranovedenie-trainer` — визуальный и технический ориентир, а не место для нового кода.
- Режимы: «Правила», «Практика ЕГЭ», «Полный вариант», «Банк и ошибки».
- Задание допускает три или четыре исходных варианта ответа. Полный вариант содержит ровно по одному проверенному заданию для каждой позиции 15–27.
- Разбор ошибки привязан к конкретному неверному варианту. Общая фраза «повторите правило» недостаточна для статуса готового задания.
- Источники и год формата остаются в данных. Задания ФИПИ и сгенерированные задания не смешиваются без маркировки.

## Предлагаемая структура

| Путь | Ответственность |
| --- | --- |
| `sources/` | Копии переданных исходных материалов и их перечень; формат определится после получения базы |
| `data/topics.json` | Темы, коды кодификатора и связи с правилами |
| `data/rules.json` | Проверенные краткие объяснения и примеры |
| `data/rule-checks.json` | Вопросы на распознавание и применение правил |
| `data/questions.json` | Канонический банк экзаменационных заданий |
| `data/review/` | Отчёты импорта, дубликатов, сомнительных ключей и редакторской проверки |
| `scripts/import_*.py` | Адаптеры под реальные форматы базы ФИПИ и выгрузки навыка |
| `scripts/validate.py` | Проверка схемы, полноты, ссылок и готовности заданий |
| `src/` | Интерфейс и чистая логика отбора, варианта, проверки ответа и прогресса |
| `test/` | Проверки банка, логики квиза и основных пользовательских сценариев |
| `.github/workflows/pages.yml` | Проверка и публикация статического сайта |

## Этап 1. Исходники и формат банка

- [ ] Получить образец базы ФИПИ, ключи ответов, год материалов и доступную выгрузку навыка генерации; зафиксировать их форматы и происхождение в `sources/README.md`.
- [ ] По нескольким заданиям каждого типа проверить извлечение номера, условия, вариантов, ключа и источника. Для 20 и 21 проверить поддержку трёх вариантов.
- [ ] Составить `data/topics.json` по кодификатору с отдельными метками для номера задания и грамматической темы; сверить с реальными заданиями банка.

**Готово, когда:** понятен путь от каждого исходного файла до записи банка, а непрочитанные поля и отсутствующие ключи перечислены отдельно.

## Этап 2. Канонические данные и проверки

- [ ] Определить схему задания: `id`, `taskNumber`, `formatYear`, `origin`, `sourceRef`, `prompt`, `stem`, `options`, `correctOptionId`, `topicIds`, `ruleIds`, `explanation`, `reviewStatus`.
- [ ] Импортировать исходные задания без тихой правки формулировок; сохранять исходный порядок вариантов и постоянные ID.
- [ ] Выявлять дубликаты, расхождения ключей и неполные записи; спорные вопросы выводить в отчёт и исключать из основных раундов.
- [ ] Проверять инварианты: номер в диапазоне 15–27, три или четыре варианта, один ключ, существующие связи с темами и правилами, объяснение правильного и каждого неверного варианта для статуса `ready`.

**Готово, когда:** повторный импорт даёт тот же банк, а намеренно испорченный тестовый вопрос не проходит валидацию.

## Этап 3. Правила и вопросы по теории

- [ ] Подготовить короткие карточки правил: формулировка, условия употребления, пара контрастных примеров, типичная ошибка и ссылки на задания.
- [ ] Добавить отдельные вопросы «по определению выберите форму/слово» и «по предложению определите правило». Например, различение `就` и `才` должно объясняться через смысл предложения.
- [ ] Связать каждый вопрос по теории с одной или несколькими карточками правил и отдельным разбором ответа.

**Готово, когда:** ученик может открыть правило, ответить на связанный вопрос и перейти к экзаменационным заданиям по той же теме.

## Этап 4. Интерфейс и учебные режимы

- [ ] Взять из `lingvostranovedenie-trainer` визуальные принципы: спокойные карточки, заметные состояния ответа, адаптивность, светлую и тёмную темы; адаптировать тексты и навигацию под ЕГЭ.
- [ ] Сделать каталог правил и режим проверки правил.
- [ ] Сделать практику ЕГЭ с фильтрами по теме, номеру, источнику и состоянию «новые/ошибки/все»; показывать количество доступных вопросов до запуска.
- [ ] Сделать генератор полного варианта: ровно 13 позиций в порядке 15–27, один вопрос на позицию, ответы и результат после завершения; при нехватке банка назвать недостающие позиции.
- [ ] Показывать после ошибки разбор выбранного варианта, верный ответ, правило и контрастный пример; в полном варианте отложить разбор до результата.
- [ ] Хранить локальный прогресс в `localStorage` с версией структуры и восстановлением после перезагрузки страницы.

**Готово, когда:** сценарии работают с клавиатурой и на телефоне, не требуют сети после загрузки страницы и не теряют локальный прогресс при обычном обновлении.

## Этап 5. Пополнение и редакторская проверка

- [ ] Определить формат выгрузки из имеющегося навыка в ту же схему банка; проставлять `origin: generated`, версию спецификации и проверяемую тему.
- [ ] Собирать новые вопросы в очередь проверки. Проверять формат, единственность ответа, содержательность всех объяснений и отсутствие дубликата ФИПИ до статуса `ready`.
- [ ] Дать понятный отчёт о том, сколько заданий готово по каждой позиции и теме, чтобы видеть пробелы для полного варианта.

**Готово, когда:** новая порция заданий добавляется пересборкой данных без изменения интерфейса и без попадания непроверенного вопроса в практику.

## Этап 6. Публикация и контроль качества

- [ ] Проверить примеры с тремя и четырьмя вариантами, сортировку по двум независимым признакам, объяснение каждого неправильного выбора, нехватку заданий для варианта и сохранение прогресса.
- [ ] Проверить полный учебный путь в браузере и на узком экране: правило → вопрос по теории → практика → полный вариант → повтор ошибок.
- [ ] Настроить сборку и GitHub Pages; публиковать только после успешной проверки данных и интерфейса.
- [ ] Добавить README: как обновлять банк, проверять новые задания, запускать сборку и открывать опубликованный сайт.

**Готово, когда:** опубликованная версия проходит тот же пользовательский путь и показывает происхождение каждого задания.

## Порядок поставки

1. **Рабочий первый выпуск:** исходный банк ФИПИ, минимальный набор карточек правил, тренировка по темам и номерам, полный вариант, разбор ошибок.
2. **Наполнение:** расширение теории и банка; добавление проверенных вопросов из навыка через очередь редакторской проверки.
3. **Улучшения по использованию:** уточнение тем и объяснений по реальным ошибкам учеников. Аккаунты и сервер не нужны для этого этапа.

## Риски, которые проверяются первыми

- Реальный формат базы ФИПИ может не содержать машиночитаемый ключ или год: импорт нельзя проектировать окончательно до просмотра образца.
- В задании 26 варианты могут быть перестановками фрагментов; схема должна хранить их без потери исходных фрагментов.
- Одна грамматическая тема встречается в разных номерах, а один номер проверяет разные темы в разные годы; фильтры не должны считать номер темой.
- Пояснение, почему верен ответ, не всегда объясняет ошибку в выбранном дистракторе; статус `ready` требует отдельного разбора каждого неверного варианта.
- В отдельной теме может не хватить материала для полного варианта; полный вариант собирается по позициям всего проверенного банка, а тематический раунд — из выбранной темы.
